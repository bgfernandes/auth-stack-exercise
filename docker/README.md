# Compose stack

What each service in `docker-compose.yml` is for, and the conventions the apps and later tickets follow. The architecture behind it is in [`docs/README.md`](../docs/README.md) §4 (Zitadel), §6 (SpiceDB), and §9 (security posture, including why `.env` is committed).

## Services

| Service | Image | Role | Reached at |
| --- | --- | --- | --- |
| `postgres` | `postgres` | One container, one database per service: `zitadel`, `spicedb`, `tenancy`, `documents` (`comments` in phase 5), created by `postgres/init.sql` on first start, each owned by a same-named role with the role name as password | `postgres:5432` inside compose; `localhost:5432` from the host |
| `zitadel-api` | `ghcr.io/zitadel/zitadel` | The OpenID Provider: identities, credentials, tokens, JWKS, the management and v2 APIs, the console. Configured by environment at first start (`ZITADEL_FIRSTINSTANCE_*`), including the admin user and two machine users whose personal access tokens it writes to the `zitadel-bootstrap` volume. Maps each app hostname to the host gateway so it can call the apps' back-channel logout URLs, and runs with its outbound-HTTP deny list narrowed to the link-local range (the default refuses every private address, which is every service here) | Through `proxy` only |
| `zitadel-login` | `ghcr.io/zitadel/zitadel-login` | Login V2, the login UI of Zitadel v4, served under `/ui/v2/login` on the same origin as the API; authenticates to the API with `login-client.pat` | Through `proxy` only |
| `proxy` | `traefik` | Routes one public origin, `http://auth.localtest.me:8080`, to the API and the login UI, as in Zitadel's reference compose (plain HTTP only) | `http://auth.localtest.me:8080` |
| `spicedb-migrate` | `authzed/spicedb` | One-shot: applies SpiceDB's schema migrations to the `spicedb` database and exits; retries on failure, because Tilt starts it before Postgres is healthy | |
| `spicedb` | `authzed/spicedb` | The authorization service: relationships, checks, lookups, ZedTokens. Clients present the preshared key as a bearer token over plaintext gRPC (`SPICEDB_PRESHARED_KEY`, `SPICEDB_INSECURE` in `.env`; `packages/authz` reads them with `SPICEDB_ENDPOINT`) | `spicedb:50051` inside compose; `localhost:50051` from the host |
| `redis` | `redis` | Application session store (`packages/auth`), append-only so sessions survive a restart | `redis:6379` inside compose; `localhost:6379` from the host |
| `mailpit` | `axllent/mailpit` | SMTP sink for Zitadel's verification and reset emails, with a web UI | SMTP `mailpit:1025` inside compose; UI `http://localhost:8025` |
| `bootstrap` (profiles `apps`, `bootstrap`) | built from `apps/bootstrap/Dockerfile` | One-shot: writes the SpiceDB schema (`packages/authz/schema.zed`, reporting `created`, `unchanged`, or `updated`), applies the `tenancy` and `documents` migrations (`packages/*/migrations`, copied into its image; `TENANCY_DATABASE_URL`, `DOCUMENTS_DATABASE_URL`), then, with `bootstrap.pat`, creates the Zitadel project, the `dashboard-web` application (reconciling its settings when they differ), and the `tenancy-api` API application, grants `dashboard-web` the scopes of `tenancy-api` in SpiceDB (`packages/client-scopes`), seeds `alice`, `bob`, `carol` in Zitadel and the Acme scenario of `docs/README.md` §6.3 (the organization and its roles through `packages/tenancy`, the projects, documents, and shares through `packages/documents`, every relationship TOUCHed on each run), and writes the apps' configuration to `/config`; idempotent. The reviewer path's `up` runs it before the apps, which depend on it; Tilt and CI run it as the explicit step `docker compose run --rm --build bootstrap`, which blocks until it finishes and returns its exit code | |
| `dashboard-web` (profile `apps`) | built from `apps/dashboard-web/Dockerfile` | The documents product's BFF: a standalone Next.js server with login, logout, the protected `/dashboard` listing and the edit flow (tickets 9 and 11; the documents domain in-process in phase 1), its sessions in `redis`; every login provisions the user's personal workspace (ticket 10: `tenancy-api` over HTTP for the user and the personal organization, then the documents domain in-process for the "Personal" project, on the `documents` database and `spicedb`); its entrypoint sources `/config/dashboard-web.env` (OIDC issuer, client ID, redirect URIs, `APP_URL`, `TENANCY_API_URL`) before starting, and `SESSION_SECRET`, `REDIS_URL`, `DOCUMENTS_DATABASE_URL`, and `SPICEDB_*` come from `.env` through the service's environment | `http://dashboard.localtest.me:3000` |
| `tenancy-api` (profile `apps`) | built from `apps/tenancy-api/Dockerfile` | The tenancy service (ticket 16): a Fastify resource server over `packages/tenancy`, verifying the project's bearer tokens and resolving client scopes from SpiceDB; one bundled file, its entrypoint sources `/config/apis.env` before starting; `dashboard-web` depends on it | `tenancy-api:4001` inside compose, by service name only |
| `zed` | `authzed/zed` | SpiceDB's CLI, in the `tools` profile so `up` never starts it: `pnpm authz:zed schema read`. `packages/authz` is mounted read-only at `/authz`, so `pnpm authz:validate` (`zed validate` with `--no-deps`) checks the schema file without a server | |

Every long-running service has a health check, so `docker compose up -d --wait` returns only when the stack is usable. Image tags are pinned in `.env`.

## Hostnames and ports

One hostname per origin, under `localtest.me`, which resolves to `127.0.0.1` in public DNS (`docs/README.md` §4.3, option (a)). Zitadel is `auth.localtest.me:8080` for the browser and for the containers alike: app services get `extra_hosts: ["auth.localtest.me:host-gateway"]` so the same URL works from inside compose, which keeps the OIDC issuer identical on both sides. The apps follow the same scheme because browsers scope cookies by host and ignore the port: `dashboard.localtest.me:3000`, later `tenancy.localtest.me:3001` and `comments.localtest.me:3002`. APIs listen on `4001` (`tenancy-api`), `4002` (`dashboard-api`), `4003` (`comments-api`) and are reached by service name inside compose; under Tilt they run on the host on the same ports, where the BFFs reach them at `localhost`.

## Zitadel admin

The first-instance admin is `ZITADEL_ADMIN_USERNAME` in `.env`. Zitadel suffixes a username that is not an email with the organization's domain, so the login name is `zitadel-admin@zitadel.auth.localtest.me` (organization `ZITADEL`, the default name). The console is at `http://auth.localtest.me:8080/ui/console`.

## Profiles

- No profile: the infrastructure above. This is what Tilt starts (ticket 5) while the apps run on the host.
- `apps`: the containerized apps (and, from ticket 4, the bootstrap container), for the reviewer path where everything runs in compose: `docker compose --profile apps up -d --wait --build`. App services carry `extra_hosts: ["auth.localtest.me:host-gateway"]` so they reach Zitadel at the same URL as the browser.
- `tools`: one-off CLIs run with `docker compose run --rm`, never started by `up`.

> **2026-10-15:** The bootstrap container is in the default set, not in `apps`: Tilt and the CI integration job start only the default set and need the configuration it writes. A plain `docker compose up -d --wait` therefore builds its image and runs it (it exits 0 when done; `--wait` accepts that), and the apps under `apps` depend on it with `condition: service_completed_successfully`.

> **2026-10-17:** The note above was verified only with the `apps` profile and is withdrawn. Without the profile, `docker compose up -d --wait` exits 1 on bootstrap's exit: compose accepts an exited one-shot only when a started service depends on it with `service_completed_successfully`, and bootstrap's only dependents are the apps. Bootstrap is therefore in the `apps` profile (and its own, `bootstrap`); the reviewer path is unchanged, and the two paths that start the infrastructure without the apps, the Tiltfile and the CI integration job, run it as the explicit step `docker compose run --rm --build bootstrap` after `docker compose up -d --wait`. That sequence is code, not a documented way to run the project: the root README offers `tilt up` and the `apps` profile, nothing else.

## Shared locations

- Named volume `zitadel-bootstrap`, mounted at `/bootstrap`: `bootstrap.pat` (the bootstrap machine user, which holds `IAM_OWNER`) and `login-client.pat` (used by Login V2). Read-write in `zitadel-api`, read-only in `zitadel-login` and in the bootstrap container; never mounted in an app.
- Bind mount `./.local/config/` (gitignored), mounted at `/config`: the files the bootstrap container generates: `dashboard-web.env` (OIDC issuer, client ID, redirect URIs, `APP_URL`, `TENANCY_API_URL`; later one per app), `apis.env` (issuer, project ID as the audience, JWKS URL, userinfo URL; sourced by every API), and `seed.json` (the Zitadel user IDs of the seeded users, the fixed ID of the seeded organization, and those of its projects and documents by their §6.3 labels, for the end-to-end tests). Read-write in `bootstrap`, read-only in every app; a Tilt-run process on the host reads the same directory. Bootstrap runs as root so it can write the directory on a Linux host, where Docker creates it root-owned on a clean checkout; the files it writes are therefore root-owned there (world-readable, mode 644).

## Resetting

`docker compose --profile apps down -v` removes the volumes, so the next `up` reinitializes Postgres (the init script runs again), Zitadel (a new instance, new PATs), SpiceDB, and Redis from scratch, and bootstrap registers everything again with new IDs (`./.local/config/` is overwritten). Under Tilt, `tilt down` keeps the volumes; `tilt down --delete-volumes` is the equivalent.
