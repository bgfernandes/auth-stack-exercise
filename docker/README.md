# Compose stack

What each service in `docker-compose.yml` is for, and the conventions the apps and later tickets follow. The architecture behind it is in [`docs/README.md`](../docs/README.md) §4 (Zitadel), §6 (SpiceDB), and §9 (security posture, including why `.env` is committed).

## Services

| Service | Image | Role | Reached at |
| --- | --- | --- | --- |
| `postgres` | `postgres` | One container, one database per service: `zitadel`, `spicedb`, `tenancy`, `documents` (`comments` in phase 5), created by `postgres/init.sql` on first start, each owned by a same-named role with the role name as password | `postgres:5432` inside compose; `localhost:5432` from the host |
| `zitadel-api` | `ghcr.io/zitadel/zitadel` | The OpenID Provider: identities, credentials, tokens, JWKS, the management and v2 APIs, the console. Configured by environment at first start (`ZITADEL_FIRSTINSTANCE_*`), including the admin user and two machine users whose personal access tokens it writes to the `zitadel-bootstrap` volume. Speaks plain h2c to Traefik and is told its public origin is `https://auth.localtest.me:8443` (`ZITADEL_EXTERNALSECURE=true`, `ZITADEL_EXTERNALPORT=8443`). Maps each app hostname to the host gateway so it can call the apps' back-channel logout URLs, and runs with its outbound-HTTP deny list narrowed to the link-local range (the default refuses every private address, which is every service here) | Through `proxy` only |
| `zitadel-login` | `ghcr.io/zitadel/zitadel-login` | Login V2, the login UI of Zitadel v4, served under `/ui/v2/login` on the same origin as the API; authenticates to the API with `login-client.pat`, presenting the public host and scheme (`CUSTOM_REQUEST_HEADERS`). It keeps the IdP session in a cookie set with `Secure`, which is why the origin is HTTPS (ticket 17b) | Through `proxy` only |
| `tls` | `alpine/openssl` | One-shot: `docker/tls/generate.sh` writes a development CA and a certificate for `auth.localtest.me` to `./.local/tls/` (the CA when absent, never touched afterwards; the certificate when absent, unverifiable, or near expiry), plus the dynamic configuration Traefik reads them from, and exits; `proxy` depends on it, which is what lets `up --wait` accept its exit | |
| `proxy` | `traefik` | Terminates TLS with the certificate from `./.local/tls/` (file provider, watching the directory) and routes one public origin, `https://auth.localtest.me:8443`, to the API and the login UI, with the routing of Zitadel's reference compose; no plain entrypoint is published | `https://auth.localtest.me:8443` |
| `spicedb-migrate` | `authzed/spicedb` | One-shot: applies SpiceDB's schema migrations to the `spicedb` database and exits; retries on failure, because Tilt starts it before Postgres is healthy | |
| `spicedb` | `authzed/spicedb` | The authorization service: relationships, checks, lookups, ZedTokens. Clients present the preshared key as a bearer token over plaintext gRPC (`SPICEDB_PRESHARED_KEY`, `SPICEDB_INSECURE` in `.env`; `packages/authz` reads them with `SPICEDB_ENDPOINT`) | `spicedb:50051` inside compose; `localhost:50051` from the host |
| `redis` | `redis` | Application session store (`packages/auth`), append-only so sessions survive a restart | `redis:6379` inside compose; `localhost:6379` from the host |
| `mailpit` | `axllent/mailpit` | SMTP sink for Zitadel's verification and reset emails, with a web UI | SMTP `mailpit:1025` inside compose; UI `http://localhost:8025` |
| `bootstrap` (profiles `apps`, `bootstrap`) | built from `apps/bootstrap/Dockerfile` | One-shot: writes the SpiceDB schema (`packages/authz/schema.zed`, reporting `created`, `unchanged`, or `updated`), applies the `tenancy` and `documents` migrations (`packages/*/migrations`, copied into its image; `TENANCY_DATABASE_URL`, `DOCUMENTS_DATABASE_URL`), then, with `bootstrap.pat`, creates the Zitadel project, the `dashboard-web` and `tenancy-web` applications (reconciling their settings when they differ), and the `tenancy-api` and `dashboard-api` API applications, grants `dashboard-web` the scopes of both APIs and `tenancy-web` those of `tenancy-api` in SpiceDB (`packages/client-scopes`), seeds `alice`, `bob`, `carol` in Zitadel and the Acme scenario of `docs/README.md` §6.3 (the organization and its roles through `packages/tenancy`, the projects, documents, and shares through `packages/documents`, every relationship TOUCHed on each run), and writes the apps' configuration to `/config`; idempotent. The reviewer path's `up` runs it before the apps, which depend on it; Tilt and CI run it as the explicit step `docker compose run --rm --build bootstrap`, which blocks until it finishes and returns its exit code | |
| `dashboard-web` (profile `apps`) | built from `apps/dashboard-web/Dockerfile` | The documents product's BFF: a standalone Next.js server with login, logout, the protected `/dashboard` listing and the edit flow (tickets 9 and 11; the documents domain in-process in phase 1), its sessions in `redis`; every login provisions the user's personal workspace (ticket 10: `tenancy-api` over HTTP for the user and the personal organization, then the documents domain in-process for the "Personal" project, on the `documents` database and `spicedb`); its entrypoint sources `/config/dashboard-web.env` (OIDC issuer, client ID, redirect URIs, `APP_URL`, `TENANCY_API_URL`) before starting, and `SESSION_SECRET`, `REDIS_URL`, `DOCUMENTS_DATABASE_URL`, and `SPICEDB_*` come from `.env` through the service's environment | `http://dashboard.localtest.me:3000` |
| `tenancy-web` (profile `apps`) | built from `apps/tenancy-web/Dockerfile` | The second client (ticket 17): a standalone Next.js server with login and logout, the protected `/organizations` list and the organization page (members with role controls for administrators, the sign-in policy form), every read and write an HTTP call to `tenancy-api` with the user's token, its sessions in `redis` under its own prefix and cookie name; its entrypoint sources `/config/tenancy-web.env` (OIDC issuer, client ID, redirect URIs, `APP_URL`, `TENANCY_API_URL`) before starting, and `SESSION_SECRET` and `REDIS_URL` come from `.env`. No database and no SpiceDB connection | `http://tenancy.localtest.me:3001` |
| `tenancy-api` (profile `apps`) | built from `apps/tenancy-api/Dockerfile` | The tenancy service (ticket 16): a Fastify resource server over `packages/tenancy`, verifying the project's bearer tokens and resolving client scopes from SpiceDB; one bundled file, its entrypoint sources `/config/apis.env` before starting; `dashboard-web`, `tenancy-web`, and `dashboard-api` depend on it | `tenancy-api:4001` inside compose, by service name only |
| `dashboard-api` (profile `apps`) | built from `apps/dashboard-api/Dockerfile` | The documents service (ticket 19a): a Fastify resource server over `packages/documents`, verifying the project's bearer tokens and resolving client scopes from SpiceDB, on the `documents` database, `spicedb`, and `tenancy-api` (organization names, with the caller's token); one bundled file, its entrypoint sources `/config/apis.env` before starting. Nothing calls it until ticket 19 moves `dashboard-web` onto it | `dashboard-api:4002` inside compose, by service name only |
| `zed` | `authzed/zed` | SpiceDB's CLI, in the `tools` profile so `up` never starts it: `pnpm authz:zed schema read`. `packages/authz` is mounted read-only at `/authz`, so `pnpm authz:validate` (`zed validate` with `--no-deps`) checks the schema file without a server | |

Every long-running service has a health check, so `docker compose up -d --wait` returns only when the stack is usable. Image tags are pinned in `.env`.

Everything that calls Zitadel from Node trusts the development CA through `NODE_EXTRA_CA_CERTS=/tls/ca.crt`: the bootstrap container and the four app services mount `./.local/tls/` read-only (the CA certificate is the one file they read; the keys are root-only), and the Tiltfile exports the same variable with the host path to every host-run app. The apps' own URLs stay plain HTTP, the back-channel logout URIs included, so the applications keep Zitadel's dev mode, which an `http://` redirect URI on a host other than `localhost` needs.

## Hostnames and ports

One hostname per origin, under `localtest.me`, which resolves to `127.0.0.1` in public DNS (`docs/README.md` §4.3, option (a)). Zitadel is `https://auth.localtest.me:8443` for the browser and for the containers alike: app services get `extra_hosts: ["auth.localtest.me:host-gateway"]` so the same URL works from inside compose, which keeps the OIDC issuer identical on both sides, and they trust the CA that signed its certificate (above). The apps follow the same scheme because browsers scope cookies by host and ignore the port: `dashboard.localtest.me:3000`, `tenancy.localtest.me:3001`, later `comments.localtest.me:3002`; `zitadel-api` maps each one to the host gateway, since Zitadel resolves an application's back-channel logout URI when the application is registered. APIs listen on `4001` (`tenancy-api`), `4002` (`dashboard-api`), `4003` (`comments-api`) and are reached by service name inside compose; under Tilt they run on the host on the same ports, where the BFFs reach them at `localhost`.

## Zitadel admin

The first-instance admin is `ZITADEL_ADMIN_USERNAME` in `.env`. Zitadel suffixes a username that is not an email with the organization's domain, so the login name is `zitadel-admin@zitadel.auth.localtest.me` (organization `ZITADEL`, the default name). The console is at `https://auth.localtest.me:8443/ui/console`.

## Profiles

- No profile: the infrastructure above. This is what Tilt starts (ticket 5) while the apps run on the host.
- `apps`: the containerized apps (and, from ticket 4, the bootstrap container), for the reviewer path where everything runs in compose: `docker compose --profile apps up -d --wait --build`. App services carry `extra_hosts: ["auth.localtest.me:host-gateway"]` so they reach Zitadel at the same URL as the browser.
- `tools`: one-off CLIs run with `docker compose run --rm`, never started by `up`.

> **2026-10-15:** The bootstrap container is in the default set, not in `apps`: Tilt and the CI integration job start only the default set and need the configuration it writes. A plain `docker compose up -d --wait` therefore builds its image and runs it (it exits 0 when done; `--wait` accepts that), and the apps under `apps` depend on it with `condition: service_completed_successfully`.

> **2026-10-17:** The note above was verified only with the `apps` profile and is withdrawn. Without the profile, `docker compose up -d --wait` exits 1 on bootstrap's exit: compose accepts an exited one-shot only when a started service depends on it with `service_completed_successfully`, and bootstrap's only dependents are the apps. Bootstrap is therefore in the `apps` profile (and its own, `bootstrap`); the reviewer path is unchanged, and the two paths that start the infrastructure without the apps, the Tiltfile and the CI integration job, run it as the explicit step `docker compose run --rm --build bootstrap` after `docker compose up -d --wait`. That sequence is code, not a documented way to run the project: the root README offers `tilt up` and the `apps` profile, nothing else.

## Shared locations

- Named volume `zitadel-bootstrap`, mounted at `/bootstrap`: `bootstrap.pat` (the bootstrap machine user, which holds `IAM_OWNER`) and `login-client.pat` (used by Login V2). Read-write in `zitadel-api`, read-only in `zitadel-login` and in the bootstrap container; never mounted in an app.
- Bind mount `./.local/tls/` (gitignored), mounted at `/tls`: what the `tls` one-shot generates: `ca.key` and `ca.crt` (the development CA; the certificate is what a reviewer imports into the browser, root README), `auth.localtest.me.key` and `.crt` (Zitadel's certificate, 825 days, the longest macOS accepts), and `traefik.yml` (Traefik's dynamic TLS configuration). Read-write in `tls`, read-only in `proxy`, bootstrap, and every app; the keys are mode 600 and the certificates 644, so an app container, which runs as `node`, reads the CA alone, and a Linux CI runner reads it for `curl --cacert`.
- Bind mount `./.local/config/` (gitignored), mounted at `/config`: the files the bootstrap container generates: `dashboard-web.env` and `tenancy-web.env` (per BFF: OIDC issuer, client ID, redirect URIs, `APP_URL`, `TENANCY_API_URL`), `apis.env` (issuer, project ID as the audience, JWKS URL, userinfo URL; sourced by every API), and `seed.json` (the Zitadel user IDs of the seeded users, the fixed ID of the seeded organization, and those of its projects and documents by their §6.3 labels, for the end-to-end tests). Read-write in `bootstrap`, read-only in every app; a Tilt-run process on the host reads the same directory. Bootstrap runs as root so it can write the directory on a Linux host, where Docker creates it root-owned on a clean checkout; the files it writes are therefore root-owned there (world-readable, mode 644).

## Resetting

`docker compose --profile apps down -v` removes the volumes, so the next `up` reinitializes Postgres (the init script runs again), Zitadel (a new instance, new PATs), SpiceDB, and Redis from scratch, and bootstrap registers everything again with new IDs (`./.local/config/` is overwritten). Under Tilt, `tilt down` keeps the volumes; `tilt down --delete-volumes` is the equivalent. `./.local/tls/` is a bind mount, so neither removes it and the CA survives a reset; deleting `.local/` makes the next start generate a new CA, which a browser that imported the old one has to import again.
